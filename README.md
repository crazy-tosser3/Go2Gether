# STOLOTO — платформа совместных спортивных активностей (backend)

REST API для поиска и проведения любительских спортивных мероприятий: лента с фильтрами, свободная запись и запись по заявке с листом ожидания, организации с модерацией, обсуждения, внутренние уведомления, рекомендации, баннеры безопасности и админ-панель.

В репозитории `StolotoSportBack` находится только backend. Веб-клиента здесь нет, поэтому все сценарии ниже проверяются через Swagger UI (встроен в приложение) или `curl`. Документ разбит по разделам критериев оценки кейса «Платформа совместных спортивных активностей» (техническая часть — разделы 3–5); соответствие критериев и разделов README — в [навигации](#навигация-по-критериям-оценки). Описана фактическая реализация по коду и результатам запуска.

## Раздел 3. Архитектурное решение

Критерии: «Архитектура и модель данных», «Обоснованность технических решений и возможность развития».

### Архитектура

#### Что делает backend

Backend хранит все данные платформы и выполняет всю бизнес-логику: учётные записи и профили, каталог направлений, организации и их модерацию, мероприятия и их жизненный цикл, запись и заявки с листом ожидания, обсуждения, уведомления, рекомендации, баннеры безопасности, админ-панель и журнал модерации. Клиент (веб или мобильный) общается с ним только по REST `/api/v1`.

#### Слои

```
HTTP-запрос
  │
  ▼  security/  — SecurityHeadersFilter → RateLimitFilter → StaleJwtCookieFilter → JWT (cookie или Bearer)
  │              SecurityConfig: URL-правила (публичное чтение, /admin/** только ADMIN, остальное — вход)
  ▼  Controller/ — маршрутизация, @Valid для DTO, без бизнес-логики
  ▼  Services/   — бизнес-правила, проверки владения (IDOR), статусы, уведомления, аудит, кэш
  │              CurrentUser.require() — текущий активный пользователь
  ▼  repository/ — Spring Data JPA: методы-запросы, Specification для фильтров, SELECT … FOR UPDATE
  ▼  PostgreSQL (схема и ограничения — Flyway)        Redis (токены, кэш страниц)
```

- **Контроллеры** (`Controller/*Controller.java`) только принимают DTO из `DTO/`, запускают Bean Validation и вызывают один метод сервиса. Пример: `EventController.join` → `ParticipationService.join`.
- **Доменные сервисы** (`Services/*Service.java`) содержат всю логику: `EventService` (создание, правка, отмена, модерация, видимость), `ParticipationService` (запись, решения по заявкам, лист ожидания), `OrganizationService` (подача, модерация, публичная видимость), `CommentService`, `NotificationService`, `AuditService`, `UserService`, `RecommendationService`, `SafetyService`, `AdminService`. Каждый сервис помечен `@Transactional`.
- **Доступ к данным** — интерфейсы в `repository/`. SQL руками не пишется, кроме блокировки `EventRepository.findByIdForUpdate`. Сущности в `Models/` хранят внешние ключи как `Long`, без ленивых связей JPA; сборкой ответов занимается `Services/DtoMapper.java`.
- **Кэш** (`cache/PageCache.java`, `cache/CacheRegions.java`) встроен в сервисы: публичные ответы читаются из Redis, после коммита изменяющей транзакции сбрасывается версия региона.
- **Ошибки**: сервисы бросают `exception/ApiException` (`notFound`, `forbidden`, `conflict`, `gone`, `validation`), `GlobalExceptionHandler` превращает их в `{"error": {"code", "message", "fields"}}`.

#### Где проверяются права

| Уровень | Где | Что проверяет |
|---|---|---|
| URL | `config/SecurityConfig.java` | Аноним / вошедший / `ADMIN`. `/api/v1/admin/**` — только `ADMIN`; явный список публичных `GET`; всё остальное — `authenticated()` |
| Пользователь | `security/CurrentUser.java` | Токен валиден, `jti` есть в Redis, пользователь `is_active = true` |
| Объект | методы сервисов | Организатор ли (`DtoMapper.isOrganizer`), владелец ли организации и одобрена ли она (`OrganizationService.requireApprovedOwned`), автор ли комментария, в каком статусе мероприятие и заявка |

Интерфейс клиента права не определяет: любая операция, скрытая на фронтенде, всё равно проверяется на сервере.

### Модель данных

ER-диаграмма и таблица ограничений целостности — в [docs/er-diagram.md](docs/er-diagram.md).

| Сущность (таблица) | Назначение | Где статус |
|---|---|---|
| `users` | Пользователи и администраторы, профиль и анкета онбординга | `role` (`USER`/`ADMIN`), `is_active`, `is_demo` |
| `sports` | Каталог направлений, в том числе добавленных пользователями | `is_custom` |
| `organizations` | Клубы, сообщества, федерации, компании | `status` (`PENDING`/`APPROVED`/`REJECTED`), `reject_reason`, `decided_by` |
| `events` | Мероприятия | `status` (`PUBLISHED`/`UNPUBLISHED`/`DELETED`/`CANCELLED`), `moderation_reason`, `cancel_reason` |
| `registrations` | Записи и заявки (`Participation`) | `status` (`PENDING`/`CONFIRMED`/`REJECTED`/`CANCELLED`/`WAITLIST`), `decision_reason`, `waitlist_position` |
| `comments` | Обсуждение мероприятия, один уровень ответов | `is_hidden`, `hidden_reason` |
| `notifications` | Внутренние уведомления | `type`, `is_read` |
| `event_reports` | Жалобы пользователей на мероприятия | `status` (`PENDING`/`ACCEPTED`/`REJECTED`), `reason`, `resolution_note` |
| `audit_log` | Журнал действий администратора | `action` |
| `user_sports`, `user_sport_levels`, `user_preferred_times` | Интересы, уровни по видам, удобное время | — |
| `safety_banners`, `safety_slides` | Карточки первой помощи и ТБ | `is_published` |

Отношения ролей:

- **Пользователь** — строка `users` с `role = USER`.
- **Представитель организации** — тот же `USER`, указанный в `organizations.owner_id`. Отдельной роли нет; у одного пользователя может быть несколько организаций.
- **Организатор мероприятия** — либо пользователь (`events.organizer_user_id`), либо организация (`events.organizer_org_id`); ровно одно из полей заполнено (`CHECK chk_one_organizer`). Права организатора у организации получает её владелец.
- **Администратор** — `users.role = ADMIN`; его решения записываются в `organizations.decided_by`, `events.moderated_by`, `comments.hidden_by`, `audit_log.admin_id`.

### Стек и обоснование решений

| Технология | Назначение в проекте | Почему | Ограничения |
|---|---|---|---|
| Java 25, Spring Boot 4.1.1 (Web MVC) | REST API, DI, транзакции | Зрелый стек команды, быстрый старт без инфраструктурного кода | Нужна JDK 25 |
| Spring Data JPA (Hibernate) | Репозитории, `Specification` для фильтров ленты | Параметризованные запросы без ручного SQL, `@Version` и блокировки «из коробки» | Связи между сущностями не смоделированы, `DtoMapper` делает отдельные запросы на каждую карточку (N+1 в ленте сглаживается кэшем) |
| PostgreSQL 18 | Основное хранилище | Enum-типы, частичные и GIN-индексы, `CHECK`, `SELECT … FOR UPDATE` | Требуется отдельный сервер; SQLite не поддерживается (миграции используют Postgres-синтаксис) |
| Flyway | Схема и демо-данные (`V01`–`V18`) | Воспроизводимая БД одной командой запуска, `ddl-auto=none` | Демо-данные — часть миграций, их нельзя «выключить» флагом |
| Redis 7 | Белый список JWT, Spring Cache, `PageCache` | Мгновенный отзыв токенов при logout и удалении аккаунта; кэш горячих страниц | Обязателен: без Redis вход работает, но любой запрос с токеном получает `401` (fail-closed) |
| Spring Security + OAuth2 Resource Server | Проверка JWT HS256, URL-правила | Стандартная валидация подписи, `iss`, `exp` | Только две роли (`USER`, `ADMIN`) |
| argon2-jvm | Хеширование паролей Argon2id | Современный алгоритм; BCrypt-хеши из ранних миграций тоже проверяются | — |
| Bucket4j | Rate limit по IP в приложении | Защита входа и записи без внешнего сервиса | Хранится в памяти процесса; доверяет `X-Forwarded-For` |
| Bean Validation | Валидация DTO | Декларативные ограничения, единый `422` | Тексты ошибок полей — стандартные английские (`must be a future date`) |
| springdoc-openapi 3.1.1 | Swagger UI | Основной «интерфейс» для проверки без фронтенда | Открыт на уровне приложения |
| Spring Boot Actuator | `/actuator/health`, `/actuator/metrics` | Проверка запуска, метрика кэша `stoloto.page.cache` | `metrics` только для `ADMIN` |
| Lombok | Геттеры/сеттеры сущностей | Меньше шаблонного кода | — |
| JUnit 5, MockMvc, spring-security-test | Интеграционные и модульные тесты | Тесты API без поднятия HTTP-сервера | Нужны живые Postgres и Redis (Testcontainers удалены в `ea8e2f9`) |
| nginx (`nginx.conf`) | Reverse proxy, второй рубеж лимитов | Защита от медленных атак и перебора до приложения | Только HTTP (80), в compose не входит |

В `pom.xml` также подключены `spring-boot-starter-thymeleaf`, `thymeleaf-extras-springsecurity6`, `mapstruct` и `caffeine`, но в коде они не используются (шаблонов и мапперов MapStruct нет).

#### Возможность развития

Что можно менять без переработки, исходя из текущего устройства кода:

- **Новое спортивное направление** не требует кода: пользователи добавляют его сами (`POST /sports` или `sport_name` при создании мероприятия), команда — строкой в миграции.
- **Новый тип уведомления или действия модератора** — значение в enum (`NotificationType`, `AuditAction`), `ALTER TYPE … ADD VALUE` в новой миграции и вызов `NotificationService.notify` / `AuditService` из сервиса (так добавлены `NEW_COMMENT` в `V17`, `EVENT_RESTORED` в `V10`, `REPORT_RESOLVED` и `REPORT_REJECTED` в `V18`).
- **Новое поле мероприятия или профиля** — миграция `ALTER TABLE`, поле в сущности, DTO и `DtoMapper`; старые миграции не меняются (Flyway версионирует схему).
- **Новый фильтр ленты** — ещё один предикат в `EventService.spec` и параметр в `EventController.search`.
- **Внешние интеграции** (уведомления по email, карты, проверка организаций) встраиваются в соответствующий сервис: точки вызова уже собраны в одном месте (`NotificationService.notify`, `OrganizationService.approve`).

Что потребует заметной переработки: связи JPA между сущностями отсутствуют (`DtoMapper` делает отдельные запросы), лимиты запросов и демо-вход живут в памяти и коде без флагов, роли зашиты в enum из двух значений.

### Быстрый старт

**Нужно:** JDK 25, Docker, Python 3.9+ (только для проверочного скрипта). Maven ставить не надо — есть `./mvnw`. Внешних ключей и интернета приложению не требуется.

Из корня репозитория:

```bash
docker compose -f docker-compose.local.yml up -d --wait
```

```bash
cp .env.example .env
```

```bash
./mvnw spring-boot:run
```

Готово: приложение на <http://localhost:8080>, Swagger UI — <http://localhost:8080/swagger-ui.html>. При первом запуске Flyway сам создаёт схему и демо-данные (миграции `V01`–`V18`), в логе будет `Started StolotoApplication`.

**Проверить, что всё работает:**

```bash
curl -s http://localhost:8080/actuator/health
```

Ожидается `{"groups":["liveness","readiness"],"status":"UP"}`. Затем можно прогнать автоматическую проверку всех сценариев:

```bash
python3 scripts/check_scenarios.py http://localhost:8080
```

Ожидается `FAILED: 0`. Дальше — [демо-доступы](#демо-доступы) и [сценарии](#как-проходить-сценарии).

**Если не запускается:**

| Симптом | Причина и решение |
|---|---|
| `port is already allocated` на 5432 или 6379 | Порт занят другим Postgres/Redis. Остановите его или смените порты в `docker-compose.local.yml` и `DB_URL`/`REDIS_PORT` в `.env` |
| `password authentication failed` | В `.env` другой `DB_PASSWORD`; для `docker-compose.local.yml` он должен быть `change-me` |

### База данных, миграции и демо-данные

- **СУБД:** PostgreSQL. Схема — только в Flyway (`src/main/resources/db/migration`), `spring.jpa.hibernate.ddl-auto=none`.
- **Порядок:** миграции применяются автоматически при старте приложения (и при запуске тестов) по номеру версии. Отдельной команды запуска миграций нет.
- **Демо-данные** создаются миграциями: `V09__seed_data.sql` (пользователи, направления, организации, мероприятия, заявки, комментарии, уведомления), `V11` (исправленный хеш пароля), `V13` (баннеры безопасности), `V15__demo_data.sql` (ещё 7 мероприятий, записи и обсуждения с ответами), `V18__event_reports.sql` (одна нерассмотренная жалоба).
- **`config/DataSeeder.java`** запускается только на пустой таблице `users`. Так как пользователи уже созданы миграцией `V09`, на практике он всегда пишет в лог `база уже заполнена, пропускаем.` (проверено на чистой БД). Его набор данных (11 мероприятий, теннис, плавание, велосипед) в базу не попадает.
- **`config/DemoDatesRefresher.java`** при каждом старте сдвигает прошедшие мероприятия демо-аккаунтов (`PUBLISHED` и `UNPUBLISHED`) вперёд на целое число недель с сохранением дня недели и времени. Поэтому демо-лента не пустеет. Мероприятия обычных пользователей не трогаются.

#### Как войти

- **Быстрый демо-вход без пароля** (бэкенд-часть «демо-панели»): `GET /api/v1/auth/demo-accounts` возвращает список `{id, name, email, role, description}`, затем `POST /api/v1/auth/login` с телом `{"demo_account_id": 1}`. Работает только для пользователей с `is_demo = true`.
- **Обычный вход:** `POST /api/v1/auth/login` с телом `{"email": "user@demo.local", "password": "Demo1234!"}`.

Токен приходит **только в cookie** `jwt` (`HttpOnly`, `Secure`, `SameSite=Strict`), в теле ответа его нет. Браузеры и `curl` отправляют `Secure`-cookie на `http://localhost`, поэтому:

- **Swagger UI:** выполнить `POST /auth/login` прямо в Swagger — cookie установится, следующие запросы пойдут от этого пользователя. Для смены роли снова выполнить `login` с другим `demo_account_id`. Кнопка «Authorize» (Bearer) не нужна.
- **curl:** сохранить cookie в файл и передавать его дальше:

  ```bash
  curl -s -c admin.txt -X POST http://localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' -d '{"demo_account_id":5}'
  ```

  ```bash
  curl -s -b admin.txt http://localhost:8080/api/v1/auth/me
  ```

По обычному HTTP на другом хосте (не `localhost`) браузер `Secure`-cookie не отправит — нужен HTTPS или заголовок `Authorization: Bearer <значение cookie>`.

Демо-часов и управления демонстрационным временем в проекте нет; единственный механизм, связанный со временем, — `DemoDatesRefresher` (см. выше).

### Сценарий 1. Создание мероприятия пользователем

**Цель:** пользователь публикует мероприятие от своего имени, другой пользователь находит его.
**Роль:** user@demo.local (id 1). **Проверяющая роль:** user2@demo.local (id 2).
**Начальные условия:** нет.

1. Войти как 1. `GET /sports` — каталог из 10 направлений с `id`, `name`, `category`, `icon`.
2. `POST /events` (Event):

   ```json
   {
     "title": "Вечерний футбол во дворе",
     "sport_id": 1,
     "starts_at": "2026-12-01T12:00:00Z",
     "ends_at": "2026-12-01T14:00:00Z",
     "city": "Красноярск",
     "address": "Красноярск, ул. Ленина 1",
     "level": "amateur",
     "requirements": "Сменная обувь",
     "equipment": "Мяч есть",
     "join_mode": "open",
     "capacity": 10
   }
   ```

   Ожидается `201`, `status: "published"`, `organizer: {"type": "user", "id": 1, ...}`, `is_organizer: true`. Мероприятие публикуется сразу, без модерации.
3. Войти как 2. `GET /events?q=Вечерний` — мероприятие в `items`. `GET /events/{id}` — карточка с организатором «Алексей Петров», `is_organizer: false`.
4. Мероприятие видно и в `GET /users/1` (публичный профиль, раздел `created_events`) и у автора в `GET /users/me/events`.

**Новое направление.** Вместо `sport_id` передать `"sport_name": "Падел"`. Ожидается `201` и `sport: {"name": "Падел", "is_custom": true}`; направление появляется в `GET /sports`. Повторное создание с `"sport_name": "  падел "` использует то же направление (нормализация: `trim`, нижний регистр, `ё→е`, схлопывание пробелов, уникальный индекс). Добавить направление отдельно можно через `POST /sports` `{"name": "...", "category": "other"}`.

**Правила валидации** (`DTO/event/CreateEventRequest.java`, `EventService.create`):

| Поле | Правило | Ошибка |
|---|---|---|
| `title` | обязательно, ≤ 200 | `422 VALIDATION_ERROR` |
| `sport_id` / `sport_name` | одно из двух; `sport_id` должен существовать; `sport_name` ≤ 60 | `422` |
| `starts_at` | обязательно, в будущем | `422`, `must be a future date` |
| `ends_at` | позже `starts_at` | `422` |
| `address` | обязательно, ≤ 500 | `422` |
| `join_mode` | `open` или `approval` | `422` |
| `capacity` | ≥ 1; не указано — без лимита | `422` |
| `lat` / `lng` | −90..90 / −180..180 | `422` |
| `level` | `beginner`, `amateur`, `pro` | `400 BAD_REQUEST` при неизвестном значении |
| без входа | — | `401` |

**Автотест:** `scripts/check_scenarios.py`, блок «Scenario 1». **Ограничения:** точные координаты, `location_note` и контакты организатора видны только организатору, администратору и подтверждённым участникам; в ленте координаты округлены до 0,01°.

### Сценарий 2. Допуск организации и публикация события

**Цель:** организация проходит модерацию и публикует мероприятие от своего имени.
**Роли:** org2@demo.local (4) — представитель, admin@demo.local (5) — администратор, user@demo.local (1) — посетитель.
**Начальные условия:** в базе есть «Гамбит» (id 2, `pending`) и «Ультра» (id 3, `rejected`) пользователя 4.

Подача новой заявки (проверяется отдельно): `POST /organizations` (Organization) с `{"name": "...", "type": "club", "contacts": "+7 900 000-00-00", "city": "Красноярск"}` → `201`, `status: "pending"`. Обязательны `name`, `type` (`club`, `community`, `federation`, `company`) и `contacts`.

**Ветка «одобрение»:**

1. Войти как 1. `GET /organizations/2` → `404`: неодобренная организация видна только владельцу и админу.
2. Войти как 4. `POST /events` с `"organization_id": 2` → `403 FORBIDDEN`, «Организация ещё не допущена».
3. Войти как 5. `GET /admin/organizations?status=pending` (Admin) — «Шахматный кружок «Гамбит»» в списке. `GET /admin/organizations/2` — карточка, владелец, мероприятия.
4. `POST /admin/organizations/2/approve` → `status: "approved"`. Повторный вызов → `409 ALREADY_REVIEWED`.
5. Войти как 4. `GET /organizations/my` — статус `approved`; `GET /notifications` — уведомление `org_approved`.
6. `POST /events` с `"organization_id": 2` (поля как в сценарии 1, `"sport_id": 2`) → `201`, `organizer: {"type": "organization", "id": 2}`. Повторного согласования нет.
7. Войти как 1 (или без входа). `GET /organizations/2` и `GET /organizations/2/events` — страница организации и её мероприятие; `GET /organizations` — организация в каталоге.

**Ветка «отказ»:**

1. Войти как 4. `GET /organizations/my` — у «Ультры» (id 3) `status: "rejected"` и `reject_reason`.
2. `POST /organizations/3/resubmit` → `status: "pending"`, причина очищается.
3. Войти как 5. `POST /admin/organizations/3/reject` с `{"reason": "Нет расписания"}` → `status: "rejected"`. Причина обязательна (`422` без неё).
4. Войти как 4. `GET /organizations/my` — `reject_reason: "Нет расписания"`; `GET /notifications` — `org_rejected` с причиной в тексте. `POST /events` с `"organization_id": 3` → `403`.

Публиковать от имени организации может только её владелец: другой пользователь получит `403 «Вы не владелец этой организации»`. Все решения админа пишутся в `GET /admin/audit-log`.

**Автотест:** `scripts/check_scenarios.py`, «Scenario 2» (обе ветки на новой организации). **Ограничения:** администратор не получает уведомления о новых и повторно поданных заявках — он видит их в `GET /admin/organizations?status=pending` и в счётчике `GET /admin/dashboard`. Одобренную организацию отозвать нельзя; после одобрения владелец может менять её данные без повторной модерации.

### Сценарий 3. Свободное присоединение

**Цель:** пользователь записывается на мероприятие со свободной записью и сразу становится участником.
**Роли:** user2@demo.local (2) — участник, user@demo.local (1) — организатор мероприятия 12.
**Начальные условия:** мероприятие 12 «Баскетбол 3×3 на набережной» (`open`, 12 мест, участников нет).

1. Войти как 2. `GET /events?join_mode=open` — мероприятие 12 в ленте. `GET /events/12` — условия: `requirements`, `equipment`, `level`, `capacity`, `confirmed_count`.
2. `POST /events/12/join` с `{}` (Event) → `201`, `message: "Вы записаны"`, `participation.status: "confirmed"`. В ответе — полная карточка с контактами организатора.
3. `GET /events/12/my-participation` → `confirmed`; `GET /users/me/participations` — мероприятие в списке.
4. Войти как 1. `GET /events/12/participants` → `count: 1`, участник «Мария Иванова» с `email` (контакты видит только организатор и админ). Без входа тот же запрос вернёт имя без email.

**Альтернативные ветки:** повторный `join` → `409 ALREADY_JOINED`; запись на своё мероприятие → `409 OWN_EVENT`; на прошедшее → `409 EVENT_PAST`; на снятое → `410 EVENT_UNAVAILABLE`; если мест нет → `status: "waitlist"`, `message: "Мест нет — вы в листе ожидания"` (позиция в очереди хранится в БД, в ответ не выводится). `DELETE /events/12/join` отменяет запись (`cancelled`) и автоматически продвигает первого из листа ожидания (`waitlist_promoted`). Параллельные записи сериализуются блокировкой строки мероприятия и не превышают `capacity`.

**Автотест:** `scripts/check_scenarios.py`, «Scenario 3».

### Сценарий 4. Участие по заявке

**Цель:** организатор принимает или отклоняет заявку, обе стороны видят актуальный статус.
**Начальные условия:** сидовые заявки `id 2` (user@demo.local → мероприятие 2 клуба org@demo.local) и `id 7` (user2@demo.local → мероприятие 7 пользователя user@demo.local), обе `pending`.

**Подача заявки** (на любом `approval`-мероприятии, например 5 «Ночное ориентирование» пользователя 2): войти как 1, `POST /events/5/join` с `{"message": "Бегаю 3 года"}` → `message: "Заявка на рассмотрении"`, `status: "pending"`; организатор получает уведомление `new_registration`.

**Ветка «принятие»:**

1. Войти как 3 (org@demo.local). `GET /events/2/requests` (Event) — заявка `participation_id: 2` от «Алексей Петров», `status: "pending"`, с `message` и email.
2. `POST /participations/2/approve` (Participation) → `status: "confirmed"`.
3. Войти как 1. `GET /events/2/my-participation` → `confirmed`; `GET /notifications` — `registration_confirmed` «Заявка принята».
4. Войти как 3. `GET /events/2/participants` — «Алексей Петров» среди подтверждённых.

**Ветка «отклонение»:**

1. Войти как 1. `GET /events/7/requests` — заявка `participation_id: 7` от «Мария Иванова».
2. `POST /participations/7/reject` с `{"reason": "Нужен средний уровень"}` → `status: "rejected"`, `decision_reason` заполнен. Причина необязательна.
3. Войти как 2. `GET /events/7/my-participation` → `status: "rejected"`, `decision_reason: "Нужен средний уровень"`; `GET /notifications` — `registration_rejected` с причиной.
4. `POST /events/7/join` → `409 REJECTED`: отказ окончательный, повторно подать заявку на это мероприятие нельзя (`d8ae9d4`).

**Альтернативные ветки:** повторное решение → `409 ALREADY_REVIEWED`; решение не организатора → `403`; принятие при заполненных местах → `409 NO_SEATS`; решения по прошедшему или снятому мероприятию → `409 EVENT_PAST` / `410`. Список заявок по другому статусу: `GET /events/{id}/requests?status=rejected`.

**Автотест:** `scripts/check_scenarios.py`, «Scenario 4» (обе ветки); `SecurityTests` TC-072 (повторная заявка после отказа).

### Сценарий 5. Уточнение условий

**Цель:** вопрос участника и ответ организатора видны в обсуждении мероприятия с понятным авторством.
**Роли:** user2@demo.local (2) спрашивает, user@demo.local (1) — организатор мероприятия 12.
**Начальные условия:** нет. Пример готовой переписки — `GET /events/11/comments` (ответ от имени ФК «Дворовые легенды»).

1. Войти как 2. `POST /events/12/comments` с `{"text": "Мяч нужен свой?"}` → `201`, `author.name: "Мария Иванова"`, `is_organizer: false`, `event_id: 12`.
2. Войти как 1. `GET /notifications` — `new_comment` «Новый вопрос в обсуждении» со ссылкой `event_id: 12`.
3. `POST /events/12/comments` с `{"text": "Мяч принесу", "parent_id": <id вопроса>}` → `is_organizer: true`, `parent_id` = id вопроса.
4. Войти как 2. `GET /notifications` — `comment_reply` «Новый ответ».
5. Любой пользователь (и без входа): `GET /events/12/comments` — оба сообщения по времени создания, у каждого `author`, `is_organizer`, `parent_id`, `created_at`.

Связь с мероприятием проверяется на сервере: `parent_id` из другого обсуждения → `422`. Ответ на ответ привязывается к корневому сообщению. Владелец одобренной организации может писать от её имени (`"as_organization_id": 1`) — тогда в ответе заполнен `as_organization`. Автор может править (`PATCH /comments/{id}`) и удалять (`DELETE /comments/{id}`) только свои сообщения (`403` для чужих); правка ставит `is_edited: true`. Пустой текст или длиннее 2000 символов → `422`.

**Автотест:** `scripts/check_scenarios.py`, «Scenario 5»; `SecurityTests` TC-069, TC-071. **Ограничения:** писать в обсуждение может любой вошедший пользователь, запись на мероприятие не требуется. Обновления не приходят в реальном времени — клиент перечитывает список. Удаление комментария автором — физическое.

### Сценарий 6. Снятие мероприятия с публикации

**Цель:** администратор снимает мероприятие, оно исчезает из выдачи, участники уведомлены.
**Роли:** admin@demo.local (5); user2@demo.local (2) — подтверждённая участница мероприятия 1; org@demo.local (3) — посторонний.
**Начальные условия:** мероприятие 1 «Утренняя пробежка в парке» опубликовано, у него есть участница и обсуждение. Уже снятое мероприятие для просмотра — 4 «Баскетбол 3×3».

1. Войти как 5. `GET /admin/events?status=published` (Admin), `GET /admin/events/1` — карточка со всеми записями и комментариями.
2. `POST /admin/events/1/unpublish` с `{"reason": "Проверка сценария 6"}` → `status: "unpublished"`. Причина обязательна.
3. Без входа: `GET /events` — мероприятия 1 нет в ленте. `GET /events/1` → `410`:

   ```json
   {"error": {"code": "EVENT_UNAVAILABLE", "message": "Мероприятие недоступно: Проверка сценария 6", "fields": {"status": "unpublished", "reason": "Проверка сценария 6"}}}
   ```

   То же получит посторонний вошедший пользователь (войти как 3). Несуществующий id даёт `404`.
4. Войти как 2. `GET /events/1` → `200` с `status: "unpublished"` и `unavailable_reason`; `GET /events/1/my-participation` → запись осталась `confirmed`; `GET /notifications` — `event_unpublished` «Событие снято с публикации» с причиной. Организатор (войти как 1) получает такое же уведомление.
5. Попытки `POST /events/1/join` и `POST /events/1/comments` → `410`.
6. Войти как 5. `GET /admin/audit-log` — запись `event_unpublished` с причиной.

**Правило обработки записей:** статусы записей не меняются (остаются `confirmed`/`pending`/`waitlist`), уведомление получают организатор и все участники с активной записью. Записавшиеся и организатор продолжают видеть карточку. Решения по заявкам на снятом мероприятии заблокированы (`410`).

**Альтернативные ветки:** `DELETE /admin/events/{id}` с `{"reason": ...}` — статус `deleted`, уведомление `event_deleted`, поведение выдачи то же. `POST /admin/events/{id}/restore` возвращает снятое или удалённое мероприятие в `published` с уведомлением `event_restored`. Снять можно только `published` (`409 INVALID_STATUS`). Не-админ получает `403`. Снятие по жалобе пользователя — [Жалобы на мероприятия](#жалобы-на-мероприятия): при любом снятии или удалении все нерассмотренные жалобы на мероприятие закрываются как принятые, авторы получают `report_resolved`.

**Автотест:** `scripts/check_scenarios.py`, «Scenario 6»; `SecurityTests` TC-070. **Ограничения:** уведомления только внутренние (`GET /notifications`), email и push не отправляются.

### Жалобы на мероприятия

**Цель:** пользователь сообщает о проблемном мероприятии, администратор рассматривает жалобу и либо снимает мероприятие с публикации, либо отклоняет жалобу. Дополняет [сценарий 6](#сценарий-6-снятие-мероприятия-с-публикации): снятие по сигналу пользователей, а не только по инициативе администратора.
**Роли:** user@demo.local (1) и любой другой пользователь — авторы жалоб; admin@demo.local (5) — модератор; user2@demo.local (2) — организатор мероприятия 8.
**Начальные условия:** жалоба `id 1` от user@demo.local на мероприятие 8 «Зарядка во дворе», `reason: misleading`, `status: pending` (миграция `V18`).

**Подача жалобы:**

1. Войти как 3. `POST /events/3/reports` (Report) с `{"reason": "dangerous", "comment": "На набережной гололёд"}` → `201`, `status: "pending"`. Причины: `spam`, `fraud`, `offensive`, `dangerous`, `misleading`, `other` (для `other` комментарий обязателен).
2. Повторная жалоба того же пользователя на то же мероприятие до решения → `409 ALREADY_REPORTED`. После решения можно пожаловаться снова.
3. `GET /users/me/reports` — свои жалобы со статусом и `resolution_note`.

**Ветка «принятие»:**

1. Войти как 5. `GET /admin/dashboard` — `pending_reports: 1`. `GET /admin/reports?status=pending` (Admin) — жалоба `id 1`: мероприятие, автор, причина, комментарий. Фильтр по мероприятию — `?event_id=8`.
2. `POST /admin/reports/1/accept` с `{"reason": "Адрес неактуален"}` → `status: "accepted"`. Причина обязательна: она становится причиной снятия.
3. Мероприятие 8 переходит в `unpublished` через тот же механизм, что в сценарии 6: пропадает из `GET /events`, без входа `GET /events/8` → `410`, участники и организатор (войти как 2) получают `event_unpublished`, в `GET /admin/audit-log` — запись `event_unpublished`.
4. Все остальные нерассмотренные жалобы на это мероприятие тоже становятся `accepted`. Войти как 1: `GET /users/me/reports` → `accepted`, `GET /notifications` — `report_resolved` «Жалоба принята».
5. Вернуть мероприятие: `POST /admin/events/8/restore`.

**Ветка «отклонение»:**

1. Войти как 5. `POST /admin/reports/{id}/reject` с `{"reason": "Нарушений нет"}` (причина необязательна) → `status: "rejected"`; мероприятие остаётся опубликованным.
2. Автор получает `report_resolved` «Жалоба отклонена»; в журнале модерации — `report_rejected` по этому мероприятию.
3. Повторное решение по той же жалобе → `409 ALREADY_REVIEWED`.

**Правила:** жаловаться можно только вошедшим и только на опубликованное мероприятие (`410` на снятое, отменённое, удалённое); на своё мероприятие — `409 OWN_EVENT`. Организатор не видит, кто на него пожаловался. Очередь и решения — только `ADMIN` (`/api/v1/admin/**`), остальным `403`. Одна нерассмотренная жалоба на пару «пользователь — мероприятие» гарантирована и в БД (частичный уникальный индекс `uq_event_reports_pending`). Если мероприятие уже снято, `accept` только фиксирует решение по жалобе.

**Отдельный документ:** [docs/reports.md](docs/reports.md) — форматы запросов и ответов, коды ошибок, схема данных, правила закрытия жалоб.

**Реализация:** `Controller/ReportController.java`, `AdminController` (`/admin/reports…`), `Services/ReportService.java`, закрытие жалоб при снятии — `EventService.acceptReports`, модель `Models/EventReport.java`, миграция `V18__event_reports.sql`.

**Автотест:** `ReportTests` TC-080…TC-085; `scripts/check_scenarios.py`, блок «Reports». **Ограничения:** администратор не получает уведомления о новой жалобе — только счётчик `pending_reports` в дашборде и очередь; автоматического снятия по числу жалоб нет; жалобы на комментарии и пользователей не реализованы.

#### Жизненные циклы

**Организация** (`OrganizationStatus`):

```
создание ─► PENDING ──approve──► APPROVED
              │  ▲
       reject │  │ resubmit (владелец)
              ▼  │
            REJECTED
```

**Мероприятие** (`EventStatus`):

```
создание ─► PUBLISHED ──cancel (организатор, причина)──► CANCELLED
              │   ▲
   unpublish  │   │ restore (админ)
   (админ)    ▼   │
           UNPUBLISHED ──delete──► DELETED ──restore──► PUBLISHED
PUBLISHED / CANCELLED ──delete (админ)──► DELETED
```

Редактировать можно только `PUBLISHED`. `CANCELLED` восстановить нельзя.

**Жалоба** (`ReportStatus`):

```
подача ─► PENDING ──accept (админ, причина) ──► ACCEPTED  + мероприятие → UNPUBLISHED
             │      снятие/удаление мероприятия другим путём ──► ACCEPTED
             └──reject (админ) ──► REJECTED   мероприятие остаётся PUBLISHED
```

**Запись** (`ParticipationStatus`, активные — `PENDING`, `CONFIRMED`, `WAITLIST`):

```
join: open + есть места ─► CONFIRMED
      approval + есть места ─► PENDING ──approve──► CONFIRMED
                                  └──reject──► REJECTED (окончательно)
      мест нет ─► WAITLIST ──место освободилось──► CONFIRMED (open) / PENDING (approval)
любой активный ──leave──► CANCELLED ──join──► заново по правилам выше
```

## Эксплуатация

### Развёртывание

Рабочего адреса стенда в репозитории нет; проверенной процедуры развёртывания тоже нет. Что подготовлено:

- **Сборка:** `./mvnw -DskipTests package` → `target/STOLOTO-0.0.1-SNAPSHOT.jar` (проверено).
- **Запуск:** `java -jar target/STOLOTO-0.0.1-SNAPSHOT.jar` с переменными из таблицы выше. Для любого общего стенда обязательно задать свои `JWT_SECRET` и `DB_PASSWORD`.
- **БД:** PostgreSQL с правом `CREATE EXTENSION pg_trgm` (выполняется в `V04`). Миграции применяются автоматически при старте; демо-данные попадают в любую новую БД вместе с ними.
- **Redis:** обязателен.
- **Хранение файлов:** аватары пишутся на локальный диск в `AVATARS_DIR`; при нескольких экземплярах или пересоздании контейнера нужен общий том. В `docker-compose.yml` для этого объявлен том `avatars_data`.
- **Прокси:** `nginx.conf` рассчитан на nginx на хосте и приложение на `127.0.0.1:8080`, домен — заглушка `sport.example.com`, только порт 80. Снаружи закрыты `/actuator`, `/swagger-ui`, `/v3/api-docs`.
- **Контейнеры:** `Dockerfile` и сервис `app` в `docker-compose.yml` требуют доработки перед использованием (имя jar, порт, файл `docker-env`) — см. [Известные ограничения](#известные-ограничения). Для разработки есть отдельный `docker-compose.local.yml` (только Postgres и Redis).
- **После развёртывания:** проверить `GET /actuator/health`, выполнить вход демо-аккаунтом, при необходимости прогнать `scripts/check_scenarios.py` против стенда (он изменит данные).

### Безопасность

Подробно — [docs/security.md](docs/security.md). Кратко:

- **Вход:** JWT (HS256) в `HttpOnly`-cookie `jwt` (`Secure`, `SameSite=Strict`) или `Authorization: Bearer`; каждый токен хранится в Redis, поэтому `logout` и удаление аккаунта действуют сразу; пароли — Argon2id.
- **Права:** `/admin/**` только для `ADMIN` (`SecurityConfig`), владение и статусы проверяются в сервисах (защита от IDOR), всё остальное закрыто по умолчанию.
- **Злоупотребления:** лимиты запросов в приложении (Bucket4j) и в nginx, лимиты размера тела и таймауты.
- **Данные:** Bean Validation на всех запросах, `CHECK`-ограничения в БД, только параметризованные запросы JPA.
- **Заголовки и CSRF:** CSP, HSTS и др. (`SecurityHeadersFilter`); CSRF-токенов нет — API без сессий, cookie `SameSite=Strict`; CORS не настроен.
- **Аудит:** действия администратора пишутся в `audit_log`.

### Известные ограничения

#### Влияют на проверку

| Ограничение | Влияние | Обход |

#### Безопасность и эксплуатация

Перед публичным запуском стоит закрыть:

| Приоритет | Проблема | Где | Что сделать |
|---|---|---|---|
| Критично | Вход в демо-аккаунт по `demo_account_id` без пароля, а `admin@demo.local` тоже помечен как демо.
