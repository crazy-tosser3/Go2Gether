# STOLOTO — платформа спортивных мероприятий (backend)

REST API для поиска и проведения любительских спортивных событий: лента мероприятий, запись и заявки с листом ожидания, организации с модерацией, обсуждения, уведомления и админ-панель.

## Стек

| Слой | Технологии |
|---|---|
| Язык / фреймворк | Java 25, Spring Boot 4.1 (Web MVC, Data JPA, Validation, Actuator) |
| Безопасность | Spring Security, OAuth2 Resource Server (JWT HS256), Argon2id (`argon2-jvm`), Bucket4j |
| БД | PostgreSQL 18, Flyway (миграции `V01`–`V16`) |
| Кэш / сессии | Redis 7 (Spring Cache + собственный кэш страниц, белый список JWT) |
| Документация | springdoc-openapi (Swagger UI) |
| Тесты | JUnit 5, MockMvc, Testcontainers (Postgres + Redis) |
| Инфраструктура | Docker Compose, nginx как reverse proxy |

## Быстрый старт

1. Поднять Postgres и Redis:

   ```bash
   docker compose up -d postgres redis
   ```

2. Создать `.env` из примера и заполнить (минимум `DB_PASSWORD` и `JWT_SECRET`):

   ```bash
   cp .env.example .env
   ```

   ```bash
   openssl rand -base64 48
   ```

3. Запустить приложение (Flyway сам накатит схему, `DataSeeder` заполнит демо-данные на пустой базе):

   ```bash
   ./mvnw spring-boot:run
   ```

4. Открыть Swagger UI: http://localhost:8080/swagger-ui.html

## Что сделано по бэкенду

### Предметная область

- **Пользователи.** Регистрация, вход, профиль (город, о себе, аватар — пресет или загруженное фото, уровень, интересующие направления и ответы онбординга: год рождения, уровень по каждому виду, радиус, удобное время, возраст компании), публичный профиль с созданными событиями. Удаление аккаунта — мягкое: пользователь деактивируется и обезличивается, его предстоящие события отменяются с уведомлением участников, записи отменяются, освободившиеся места уходят листу ожидания. Нельзя удалить последнего админа, демо-аккаунт и владельца организаций.
- **Направления спорта.** Каталог с категориями и иконками, поиск/автодополнение. Пользователь может добавить своё направление; дубли отсекаются по нормализованному имени (`trim`, нижний регистр, `ё→е`, схлопывание пробелов) и уникальному индексу.
- **Организации.** Создание, редактирование, повторная подача после отказа. Модерация админом: `PENDING → APPROVED / REJECTED` с причиной. Неодобренная организация видна только владельцу и админу, остальным — 404. Публиковать события и писать комментарии от имени организации может только владелец одобренной организации.
- **Мероприятия.** Организатор — либо пользователь, либо организация (`CHECK` в БД). Лента с фильтрами (текст, направление, город, даты, уровень и т. д.) и пагинацией. Режимы записи `open` и `approval`, лимит мест, отмена организатором с причиной. Снятые/удалённые/отменённые события видны админу, организатору и записавшимся, остальным — `410 EVENT_UNAVAILABLE`.
- **Запись на события.** Сразу подтверждение (`open`), заявка (`approval`) или лист ожидания, если мест нет. При освобождении места первый в очереди автоматически продвигается. Организатор принимает/отклоняет заявки с причиной. Нельзя записаться на своё или прошедшее событие и дважды на одно событие.
- **Обсуждения.** Комментарии к событию с одним уровнем вложенности (ответ на ответ привязывается к корню), правка и удаление автором, ответ от имени организации, уведомление автору родительского комментария.
- **Рекомендации.** Персональная подборка событий (интересы, история записей, город, уровень, с кем играл) и «похожие события» под карточкой, с кодами причин для UI. См. [docs/recommendations.md](docs/recommendations.md).
- **Уведомления.** Внутренний «колокольчик»: заявки, решения, продвижение из очереди, изменения/отмена/снятие событий, решения по организациям, ответы в обсуждениях.
- **Админка.** Дашборд со счётчиками, модерация организаций, снятие/удаление/восстановление событий, скрытие комментариев с причиной, журнал модерации (`audit_log`), статистика и сброс кэша.

### Технические решения

- **Конкурентная запись.** `join`, `leave`, `approve`/`reject` берут строку события через `SELECT ... FOR UPDATE` (`EventRepository.findByIdForUpdate`), поэтому параллельные записи не превышают лимит мест. Плюс `UNIQUE(event_id, user_id)` в таблице записей и `@Version` на событии.
- **Миграции.** Вся схема — в Flyway, `ddl-auto=none`. Postgres-енамы для статусов, частичные индексы под ленту, лист ожидания и т. д., GIN-индекс для полнотекстового поиска, `CHECK`-ограничения (длина комментария, координаты организатора).
- **Кэширование в Redis.**
  - Spring Cache: каталог направлений, демо-аккаунты.
  - `PageCache`: готовые ответы горячих страниц (лента, карточка события, участники, комментарии, организации, профили) с отдельным TTL по регионам.
  - Инвалидация без `SCAN`/`DEL`: у региона растёт номер версии (`INCR`), старые ключи перестают читаться и умирают по TTL. Сброс выполняется только после коммита транзакции.
  - Персонализированные и привилегированные ответы (владелец, админ) идут мимо кэша, чтобы не утекли в общий.
  - Если Redis недоступен, чтение идёт напрямую в БД.
  - Метрика `stoloto.page.cache` (hit/miss/error по регионам) и заголовок `X-Cache` в ответе.
- **Единый формат ошибок.** `ErrorResponse {code, message, fields}`, валидация → `422 VALIDATION_ERROR` с полями в snake_case, бизнес-конфликты → `409` с кодом (`ALREADY_JOINED`, `NO_SEATS`, `EVENT_PAST` …), необработанные исключения логируются и отдаются как `500 INTERNAL_ERROR` без стектрейса.
- **API-конвенции.** JSON в `snake_case`, енамы в нижнем регистре (в теле и в query-параметрах регистр не важен), версия в пути `/api/v1`. Swagger показывает то же самое.
- **Наблюдаемость.** Actuator: `/actuator/health` публично, `/actuator/metrics` только для ADMIN.

## Что сделано по безопасности

### Аутентификация

- **JWT (HS256)** с claim'ами `sub` (id пользователя), `role`, `iss`, `iat`, `exp` и уникальным `jti`. Ключ берётся из `JWT_SECRET` (Base64); если он короче 32 байт, приложение не стартует.
- **Отзыв токенов.** Каждый выданный `jti` хранится в Redis (`auth:token:<jti>`) с тем же TTL. При каждом запросе декодер проверяет, что `jti` есть в белом списке, поэтому `logout` и удаление аккаунта моментально гасят токен. Если Redis недоступен, токены не принимаются (fail-closed).
- **Деактивированные пользователи** отсекаются на уровне сервисов: `CurrentUser.require()` пропускает только `is_active = true`.
- **Передача токена.** Cookie `jwt` с флагами `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; для Swagger и внешних клиентов — заголовок `Authorization: Bearer`. При logout cookie стирается (`Max-Age=0`).
- **Сессии** не создаются (`STATELESS`).

### Пароли

- Хеширование **Argon2id** (3 итерации, 64 МБ памяти). Массив символов пароля затирается после хеширования.
- Совместимость со старыми **BCrypt**-хешами (`$2…`) из ранних миграций: такие пароли проверяются через BCrypt.
- Требования при регистрации: 8–128 символов, валидный email до 254 символов. Email нормализуется (trim + нижний регистр), уникальность — индексом `LOWER(email)`.
- На неверный email и неверный пароль ответ одинаковый (`401 INVALID_CREDENTIALS`, «Неверный email или пароль»).
- Удаление аккаунта требует повторного ввода пароля; хеш затирается значением, которое не может совпасть ни с одним паролем.

### Авторизация

- Две роли: `USER` и `ADMIN`. Роль берётся из JWT (`ROLE_<role>`).
- **URL-уровень** (`SecurityConfig`): `/admin/**` и `/actuator/**` (кроме `health`) — только ADMIN; публичное чтение ленты, карточек, каталогов и профилей явно перечислено; всё остальное требует входа (`anyRequest().authenticated()` — deny by default).
- **Объектный уровень** (проверки владения в сервисах, защита от IDOR):
  - события правит/отменяет и заявки рассматривает только организатор (лично или как владелец организации);
  - организацию правит и подаёт повторно только владелец;
  - комментарий правит и удаляет только автор, скрытый модератором — править нельзя;
  - список заявок видят только организатор и админ;
  - контакты участников (email, сообщение в заявке) видят только организатор и админ, публично — имена и количество;
  - неодобренные организации и недоступные события скрыты от посторонних (`404` / `410`).
- Ответы `401`/`403` от Spring Security отдаются в том же JSON-формате, что и остальные ошибки (`JsonSecurityErrorHandler`).

### Защита от злоупотреблений

- **Rate limiting в приложении** (`RateLimitFilter`, Bucket4j, по IP): вход и регистрация — 10/мин, запись — 60/мин, чтение — 300/мин. При превышении — `429` с `Retry-After`.
- **Rate limiting в nginx** (второй рубеж): `auth` — 5/мин, запись — 30/мин, общий — 20 запросов/с, не больше 30 соединений с IP.
- **Защита от медленных атак (Slowloris)**: таймауты на заголовки, тело и отправку — по 10 с, лимит тела запроса 1 МБ, ограничения на размер заголовков.
- nginx отбрасывает запросы без корректного `Host` (`444`), разрешает только `GET/HEAD/POST/PUT/DELETE/OPTIONS`, скрывает версию (`server_tokens off`), перезаписывает `X-Forwarded-For` реальным адресом клиента, закрывает снаружи `/actuator`, `/swagger-ui`, `/v3/api-docs`.

### Валидация входных данных

- Bean Validation на всех DTO: длины строк, диапазоны координат (`-90..90`, `-180..180`), `@Future` для даты начала, `capacity ≥ 1`, лимит на число направлений в профиле и т. д.
- Ограничения дублируются в БД (`CHECK`, `NOT NULL`, внешние ключи с `RESTRICT`).
- SQL-инъекции исключены: только JPA, Spring Data и Criteria API (`Specification`) с параметрами, без конкатенации SQL.
- Некорректный JSON и неверные типы параметров → `400` без деталей реализации; неизвестные исключения не раскрывают стектрейс.

### HTTP-заголовки безопасности

`SecurityHeadersFilter` ставит на каждый ответ:

- `Content-Security-Policy`: `default-src 'self'`, `frame-ancestors 'none'`, `form-action 'self'`, `base-uri 'self'` и т. д.;
- `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`;
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy`: запрет камеры, микрофона, геолокации, платежей, USB, Bluetooth;
- `Cache-Control: no-store` на `/api/**`, чтобы ответы API не оседали в кэшах браузера и прокси.

Для Swagger UI политика мягче (`SAMEORIGIN`), иначе он не работает.

### CSRF и CORS

- CSRF-токены отключены: API stateless, а cookie с JWT помечена `SameSite=Strict`, поэтому браузер не отправит её с чужого сайта.
- CORS-источники не настроены — кросс-доменные запросы из браузера не проходят, фронтенд должен отдаваться с того же домена.

### Модерация и аудит

- Все действия администратора (одобрение/отклонение организаций, снятие/удаление/восстановление событий, скрытие комментариев) пишутся в `audit_log` с автором, целью и причиной.
- Удаления событий и комментариев модератором мягкие — данные остаются для разбора.

### Секреты

- Секреты читаются из переменных окружения / `.env`; `.env` и `*.env` в `.gitignore`, в репозитории только `.env.example`.
- Postgres и Redis в `docker-compose.yml` слушают только `127.0.0.1`.

## Известные проблемы и что доработать

Перед публичным запуском стоит закрыть:

| Приоритет | Проблема | Где | Что сделать |
|---|---|---|---|
| Критично | Вход в демо-аккаунт по `demo_account_id` без пароля, а `admin@demo.local` тоже помечен как демо. Любой может получить токен администратора. | `AuthService.login`, `DataSeeder` | Выключать демо-вход флагом (`app.demo.enabled=false` в проде) и не помечать админа как демо |
| Высокий | `RateLimitFilter` доверяет `X-Forwarded-For` от любого клиента: подставляя новый IP в каждом запросе, лимиты обходятся (боты из `bots/` так и делают). Карта бакетов растёт без ограничений между часовыми очистками. | `RateLimitFilter.getClientIp` | Доверять заголовку только от адреса nginx (или `server.forward-headers-strategy` + `RemoteIpValve`), ограничить размер карты (например, Caffeine с expiry) |
| Высокий | В `application.properties` есть значения по умолчанию для `JWT_SECRET` и пароля БД; в `docker-compose.yml` пароль Postgres записан открытым текстом. Если забыть задать переменные, прод поднимется с известным ключом подписи. | `application.properties`, `docker-compose.yml` | Убрать дефолты (падать при старте без секрета), пароль брать из `.env` |
| Средний | Нет HTTPS: nginx слушает только 80, а cookie `Secure` и HSTS рассчитаны на TLS — по HTTP браузер не отправит cookie. | `nginx.conf` | Добавить `listen 443 ssl` и редирект с 80 |
| Средний | Поля `avatar_url`, `website_url` не проверяются на схему — можно сохранить `javascript:...`, что опасно, если фронт вставит ссылку как есть. | DTO профиля/организации | `@Pattern("^https?://...")` или `@URL(protocol=...)` |
| Средний | Swagger UI и `/v3/api-docs` открыты на уровне приложения (закрыты только в nginx). | `SecurityConfig` | Отключать springdoc в прод-профиле |
| Низкий | Перебор email по времени ответа: для несуществующего email Argon2 не считается, ответ заметно быстрее. | `AuthService.login` | Сверять с фиктивным хешем, если пользователь не найден |
| Низкий | Старые BCrypt-хеши не перехешируются в Argon2 при входе. | `Argon2PasswordEncoder` | Реализовать `upgradeEncoding` / перехеширование при успешном логине |
| Инфраструктура | `Dockerfile` копирует `STOLOTO-1.0.0-RELEASE.jar`, а Maven собирает `STOLOTO-0.0.1-SNAPSHOT.jar`; `EXPOSE 8080`, а compose пробрасывает `8001`; нет файла `docker-env`; имя БД в compose (`UmirFlagman`) не совпадает с дефолтным `DB_URL` (`Stoloto`); в nginx часть `proxy_pass` указывает на `127.0.0.1:8080`, часть на `app:8080`, а лимит `write` применяется и к GET. | `Dockerfile`, `docker-compose.yml`, `nginx.conf` | Выровнять имена и порты, добавить nginx в compose |
